# 人工修改记录

本记录沿用任务一的“问题或要求、修改结果、对应位置”格式。项目成员已确认的规则来自任务一、任务二及其修改记录。本轮由 AI 对照这些规则将初稿候选方案修订为任务三文档，保留小组提交前可核对的依据。

## 1. 初稿之后的早期调整

| 初稿内容 | 早期调整 | 位置 |
|---|---|---|
| 排课候选键考虑包含教室编号。 | 一班一个时间只对应一间教室，班号与时间编号便可唯一确定教室。两列组成主键，教室编号为非空外键。 | T13、函数依赖第 2 节、关系分解第 2 节 |
| 初稿用学生与教学班唯一来阻断重复选课。 | 使用独立选课记录号。同课同学期唯一只作用于有效记录，历史允许退课后重选。 | T09、关系分解第 5 节 |
| 现有班号的最大流水可用来生成下一号。 | 删班会造成最大值回退，独立保存各学期流水上限，发号与建班同事务完成。 | T14、关系模式清单第 4 节 |

## 2. 对照任务一、任务二修正规则

| 项目成员确认的要求或复核发现 | 修改结果 | 位置 |
|---|---|---|
| 教室完整名称有固定区楼房间规则，无座位数要求。 | 教室编号为主键，完整名称为候选键。排课按行引用教室，人数限制只读班级容量。 | T12、T13 |
| 各学期独立开班，小学期在春季开学 126 天后开始。 | 学期采用学年、学期序号联合键。由所属学期限制班级排课，结束日期及窗口按规则派生。 | T05、T06、关系模式清单第 4 节 |
| 账号仅保存密码哈希。 | 保留单一哈希字段，选择 32 字节输出作为逻辑设计参数。人员账号引用须唯一且匹配角色。 | T01–T03 |
| 同一时段可以被多个班引用，同一班不同时间可换教室。 | 时间有独立主键，星期和首尾节次组成自然候选键。任课安排和排课各用独立的联合键。 | T07、T08、T13 |
| 绩点、选课状态和退课类型有明确推导依据。 | 绩点由分数换算，状态由退课时刻是否为空判断，类型按所属学期与退课时刻判定。查询保持原展示口径。 | T09、T10、函数依赖第 3 节 |
| 选退课人数和改分历史存在事务要求。 | 保留有效人数缓存，当前成绩与历史分离。分数更新和历史追加同事务，删班按外键依赖顺序清理。 | T06、T10、T11、关系模式清单第 4 节 |

## 3. 定稿前的核对

| 复核事项 | 处理结果 |
|---|---|
| 同课多班是否会被联合键误限 | 班号单独唯一，课程、学年、学期的组合可对应多个班。 |
| 1NF、2NF、3NF 是否逐个分析 | 以完整候选键和依赖闭包逐表判断，区分条件规则与普通函数依赖。 |
| 分解能否恢复原事实 | 分步列交集和可决定的子关系，区分内连接恢复原宽表与左连接获取尚无成绩的选课。 |
| 原依赖是否保留 | 把依赖基归属到子关系，用传递链推导原有间接依赖。 |
| 数据类型如何落地 | 采用环境中已有 MySQL 8.0 的数据类型。表名、字段长度、时间统一存储口径及流水字段为任务三设计选择。 |

本阶段的验证限于关系设计与推导。建库运行、外键行为和业务事务测试在后续任务按实际结果记录。
