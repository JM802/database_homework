# 关系分解与正确性证明

下文从容易出现冗余的候选模式出发，说明插入、删除、更新异常，再推导到[正式关系模式](关系模式清单.md)。记号沿用[函数依赖分析](函数依赖分析.md)。花括号内的复合记号表示一组字段。例子采用假设数据。

## 1. 判定方法

对二元分解 R → R₁,R₂，令交集 I = R₁ ∩ R₂。若在原依赖集 F 的闭包中有 I → R₁ 或 I → R₂，则该步无损。多个二元步骤逐步无损，整个分解也无损。依赖保持要求将 F 投影到各子关系，合并投影后可以推出原 F。下文直接定位每条依据的归属关系，或写出跨投影的传递链。

示例中先对每种独立联系或事实构造待分解的宽关系。任课与多个时段在查询时可组合，业务中每位任课教师占用同班全部时段。对于任意只挑若干“教师—时段”组合的数据，不能仅凭函数依赖就断定可无损拆成任课和排课。当前模型应分别保存两组事实。由关联查询组合出的报表不等同于底层关系。

## 2. 从排课宽表分离班级、课程、学期、时间和教室

设初始关系：

```text
ScheduleWide(B,T,R,room_name,W,F,L,C,course_name,Y,N,start_date,capacity,active_count)
```

依赖基为 B,T → R，R → room_name，room_name → R，T → W,F,L，W,F,L → T，B → C,Y,N,capacity,active_count，C → course_name，Y,N → start_date。以 B,T 起算能够得到全部字段。去掉 B 无法推导班级信息，去掉 T 无法得到某条具体排课。用 {W,F,L} 替代 T 也得到候选键。B → 班级字段、T → 时间字段都是对候选键真子集的依赖，宽表不满足 2NF。教室名称又受 R 决定，形成传递依赖。

| 异常 | 宽表的具体表现 |
|---|---|
| 插入 | 尚未安排教学班时，无法以完整的 B,T 为键登记新教室或共享时段 |
| 删除 | 删除某门课程最后一条排课时，课程名等资料可能随之丢失 |
| 更新 | 同一教室名称、同一班容量或同一门课程名称散落多行，局部更新会得到矛盾的记录 |

按下表依次分解。每一步“拆出”关系与剩余部分均保留交集。

| 步骤 | 拆出关系 | 交集 I | I 决定拆出关系的依据 |
|---|---|---|---|
| 1 | classroom(R,room_name) | R | R → room_name |
| 2 | weekly_time(T,W,F,L) | T | T → W,F,L |
| 3 | course(C,course_name) | C | C → course_name |
| 4 | academic_term(Y,N,start_date) | Y,N | Y,N → start_date |
| 5 | teaching_class(B,C,Y,N,capacity,active_count) | B | B → C,Y,N,capacity,active_count |

剩余 `class_schedule(B,T,R)`，保留 B,T → R。五步交集分别为拆出关系的键，所以无损。以上列出的依赖基每条都完整位于一个子关系，room_name → R 留在教室，W,F,L → T 留在上课时间。由 B→C 与 C→course_name 仍能推得 B→course_name，故传递依赖同样可推回。不同班可以引用相同 T，或在互不重叠的时段引用相同 R，班号和时间编号的同一组合只能决定一个 R。

## 3. 从人员宽表与任课宽表分离账号及基础档案

**学生账号示例。** `StudentAccount(S,A,student_name,role,hash)` 有 S→A,student_name，A→S，A→role,hash。S 和 A 都是键，这个宽表自身可达 BCNF。若将学生、教师和管理员各放一个带密码的结构，会出现管理员无学生档案难登记、统一鉴权要扫描多份账号、删除身份可能误删共享模型定义等问题。按 E-R 分成 `student(S,A,student_name)` 与 `account(A,role,hash)`。交集 A 为账号键，无损。依赖分别留在 student 与 account，S→role,hash 可通过 S→A 推得。教师账号依同样方法处理，将 S 换成 P。管理员账号在 account 单独存在。若需列全部账号并带可选档案，用从 account 出发的左连接，不能用内连接作全账号清单。人员主键与账号名的唯一性、角色匹配和互斥须分别执行。

**任课示例。** `AssignmentWide(B,P,teacher_name,A,C,Y,N,capacity,active_count)` 中，(B,P) 为键，P→teacher_name,A，A→P，B→C,Y,N,capacity,active_count。宽表因部分依赖不满足 2NF。教师尚无任课时不方便登记，只删除一条任课可能使教师资料消失，教师改名或班级人数变化会改多条任课行。按 P 拆出 teacher，按 B 拆出 teaching_class，剩余 teaching_assignment(B,P)。每一步的交集分别为 P、B，都是被拆出关系的键，故无损。两组 FD 与账号反向唯一依赖均保留在各自原子关系，任课表留存 B,P 的组合唯一性。

## 4. 分离选课、成绩与修改历史

考虑一张从已生成改分记录出发的宽表：

```text
GradeHistoryWide(H,E,P,old_score,new_score,changed_at,
                 score,first_recorded_at,S,B,selected_at,withdrawn_at)
```

有 H→E,P,old_score,new_score,changed_at，E→score,first_recorded_at，E→S,B,selected_at,withdrawn_at。更上层的学生姓名或教师姓名若出现在宽表，分别由学号或工号决定。H 能得到全部属性，为候选键。E 能决定成绩和选退课字段，却不能决定一次修改，形成以非超键为左侧、非主属性为右侧的依赖，宽表可满足 2NF，但违反 3NF。它还会导致首次录分无法用完整 H 行表达、删最后一条修改丢失当前成绩、改分时须覆盖旧修改行中重复的“当前分数”。

1. 先按 E 拆出 enrollment(E,S,B,selected_at,withdrawn_at)，交集 E 为该关系的主键。
2. 再按 E 拆出 grade(E,score,first_recorded_at)，交集 E 为成绩关系的主键。
3. 剩余 grade_revision(H,E,P,old_score,new_score,changed_at)，H 为键，E 与 P 为外键。

两步均无损，每一组原依赖都能在单个目标关系内检查。H→score 可通过 H→E 与 E→score 推导。源宽表只描述已有修改的记录，分解后的正式库还可保存无修改的成绩和未录成绩的选课。查询所有选课使用 enrollment 为主表，按需左连接 grade，再左连接 grade_revision。用内连接恢复改分宽表时，本来没有修改的选课或成绩不属于该原宽表的行集。

## 5. 派生字段的去留

| 原候选字段 | 重复保存时的问题 | 处理与信息可恢复性 |
|---|---|---|
| 学期周数、结束日期 | 学期序号决定周数，开始日期和序号共同决定结束日期。改日期可能留下过期结束日 | 按 18、18、4 周公式实时派生。只要原数据满足规则，从学期表可恢复完全相同的值 |
| 学号＋班号全局唯一 | 退课后重选时相同组合再次出现，插入被错误阻断 | 选课记录号标识事件。有效行在事务内检查同学期同课唯一，保留全部历史 |
| 选课状态、退课类型 | 同时修改退课时刻和状态可能不同步。已退记录的退课类型依赖班级学期与退课时刻 | 以退课时刻是否为空判定状态，以班级所属学期窗口判定退课类型。历史班级与学期窗口的输入保持稳定 |
| 绩点和剩余名额 | 当前分数决定绩点，容量和有效人数决定余量，多存一份会过期 | 按任务一公式计算，仍可查询。有效人数同步缓存按 BR-11 保留 |
| 现存最大班号 | 删除编号最大的班后重算会再次发放旧号 | 每学期保留独立的已发流水上限，该事实不由现存班级推导 |

上述派生列的省略是计算表达和视图设计，并非用自然连接恢复删去的列。保持公式后结果可从保留字段及既定规则恢复。任课资格、时间碰撞、办理窗口和缓存同步属于跨行或跨表业务约束，不属于这里的 FD 投影证明，落实方式见[关系模式清单](关系模式清单.md)第 4 节。
